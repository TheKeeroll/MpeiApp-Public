# Технический план обновления MpeiApp до v2.4.0

## Статус и границы

Статус: **актуализированный план к реализации**.

В этом шаге изменён только данный Markdown-документ. Исходники React Native, Android/iOS-проекты, зависимости, lock-файлы, CI, приложенный промо-арт и секреты не изменялись.

Релиз v2.4.0 включает шесть связанных направлений:

1. обновление React Native-стека, Node.js и TypeScript;
2. стабильную Android-сборку, Metro smoke-check, тесты и GitHub Actions;
3. исправление Android flow смены launcher-иконки;
4. Yandex Mobile Ads и систему токенов лояльности;
5. безопасную интеграцию DragoNet через отдельный proxy на VPS;
6. расписание для неавторизованного пользователя и Android-first порядок работ.

## Подтверждённые продуктовые решения

| Решение | Зафиксированное поведение |
| --- | --- |
| TypeScript | Использовать строго стабильный `typescript@6.0.3`, без перехода на 7.x. Версия 6 должна показать предупреждения для будущей миграции на 7.x. |
| Node.js | Фиксировать Node 24; локально подтверждён Node 24.13.0. Упоминание Node 19 удалить. |
| Реклама | До релиза использовать официальные demo ID. В `Secrets.ts` подготовить отдельные production placeholders для Android/iOS и каждого из трёх форматов. |
| Sticky banner | Обязательные места — `LoadingScreen` после успешного логина/2FA, пока загружаются и парсятся страницы БАРС, и низ экрана «Пропущенные занятия». В одном видимом экране рендерится не более одного sticky; список и действия не перекрываются. |

| DragoNet | CTA ведёт на `https://t.me/DragoNetworkBot`; приложенный арт с драконом используется фоновым изображением промо-карточки с затемняющим overlay для читаемого текста. В карточке также есть путь к бесплатному демо-доступу, чтобы открыть Telegram и купить основную подписку. |
| Проверка VPN | Запускается строго последней после завершения онлайн-парсинга БАРС. В offline-режиме запрос не выполняется и счётчики попыток не меняются. |
| Firebase | Не удаляется. Конфигурация и legacy-код остаются для будущего возврата; CI получает Android service-конфиг из GitHub Secret, а не из Git. |
| Порядок платформ | Полная реализация и проверка сначала на Android. iOS Pods, Yandex native-настройки и тестирование в VMware/Xcode выполняются только после принятого Android-этапа. |
| Гостевое расписание | В нижней навигации до входа появляется «Расписание». До введения запроса не показываются и не загружаются данные неизвестной группы: доступен только существующий поисковый блок. |

## Целевая архитектура

```text
AppEntry
├─ LoyaltyProvider
│  ├─ реальный баланс и дневные лимиты
│  ├─ покупки/разблокировки на устройстве
│  └─ глобальный TokenBadge
├─ VpnSubscriptionProvider
│  ├─ сохранённое имя клиента
│  ├─ последовательности результатов проверок
│  └─ запрос к DragoNet proxy после БАРС-парсинга
└─ AdsProvider
   ├─ вычисляет effective entitlement
   ├─ управляет adUnitId и consent
   └─ скрывает inline / sticky / rewarded при ad-free

MpeiApp ── POST { purpose: verify | demo } + Mpei-App-Req-Id ──> DragoNet HTTPS proxy
                                                                  ├─ verify: GET VPN panel /apiv2/clients
                                                                  └─ demo:   POST VPN panel /apiv2/save
                                                                     (Token, TLS key и panel URL остаются на VPS)
```

Базовые правила состояния:

```text
effectiveContentAccess = vpnActive OR locallyPurchasedUnlock
adsEnabled             = NOT vpnActive AND NOT locallyPurchasedAdsRemoval
shownTokenBalance      = vpnActive ? "∞" : realTokenBalance
```

При активном VPN реальный баланс, дневные лимиты и все купленные unlocks продолжают храниться без потери. VPN лишь временно расширяет доступ и заменяет отображаемое число на `∞`. После окончательной потери VPN повторно применяется только реально купленный пользователем доступ.

## Этап 2. Состояние загрузки БАРС и реклама на LoadingScreen

Требование «sticky после входа/2FA, пока идут страницы» нельзя надёжно реализовать поверх текущего раннего `LoginState = LOGGED_IN`: сейчас Navigator может появиться до завершения всех дополнительных загрузок. Нужны разделённые состояния аутентификации и готовности данных.

1. Выделить явную фазу `AUTHENTICATED_LOADING_DATA` (название уточняется с типами приложения): credentials/2FA успешно подтверждены, но онлайн-данные ещё собираются.
2. `LoadingScreen` отображается в этой фазе и получает нижний sticky slot от `AdsProvider`. Второй обязательный sticky slot v2.4.0 находится в `SkippedClassesScreen`; они не бывают одновременно видимы.
3. Существующую цепочку `BARS.LoadOnlineData()` перестроить так, чтобы после всех `Fetch*`, `finally` и parsing задач событие «данные готовы» отправлялось ровно один раз. VPN revalidation вызывается **последней** задачей этой цепочки.
4. Пока есть ранее сохранённый активный VPN-статус, loading sticky не рендерится: у действующего клиента не должно быть рекламной вспышки. У нового пользователя без сохранённого статуса demo sticky допустим во время загрузки.
5. После VPN-проверки `AdsProvider` обновляет состояние в текущей сессии; затем приложение переходит в обычный Navigator.
6. При offline до сетевого запроса `NetInfo`/эквивалент сразу помечает проверку как пропущенную: никакие счётчики не растут, предыдущий subscription/entitlement state остаётся применённым.
7. `AD_PLACEMENTS` явно перечисляет оба включённых sticky slots: `loading` и `skippedClasses`. В `SkippedClassesScreen` sticky размещается внизу после содержимого/с отдельным нижним `contentContainerStyle` padding, чтобы не заслонять последнюю карточку, footer или safe area. Камера QR, login/2FA, map и критичные формы остаются без sticky.

## Этап 3. Android launcher icon без дубликатов

### Причина

В текущем Android-патче `react-native-change-icon` включается новый `activity-alias`, но штатный lifecycle-механизм отключения предыдущего alias удалён: не ведётся `classesToKill`, не регистрируется callback и не вызывается `activity.finish()`. Поэтому в launcher остаются две enabled иконки.

### Изменение патча

1. Сохранить совместимые части патча:

   - Java 17 / AGP-совместимые настройки Gradle библиотеки;
   - исправленный импорт `com.android.Version`;
   - необходимые `@NonNull` annotations;
   - iOS-правку для текущего рабочего New Architecture flow.

2. Убрать только проблемную custom Android-логику `changeIcon` и восстановить штатную последовательность библиотеки:

   - определить текущий launcher component;
   - включить новый alias;
   - поставить предыдущий alias в `classesToKill`;
   - зарегистрировать ActivityLifecycleCallbacks;
   - завершить текущую Activity;
   - на pause отключить старый alias.

3. Не добавлять самостоятельный Intent/relaunch-код и не оставлять неиспользуемый `ReactApplicationContext`.

### UX

1. В `IconSelector` создать единый обработчик `requestIconChange(iconName)`.
2. На Android пользовательский выбор альтернативной иконки сначала показывает Alert: приложение закроется и автоматически перезапустится для применения выбора.
3. Кнопки: `Да, перезапустить` вызывает `BARSAPI.ChangeIcon`; `Отмена` не меняет state/UI и не перезапускает приложение.
4. На iOS сохранить текущий немедленный сценарий без Alert.
5. Повторный выбор уже активной иконки и rejected Promise не должны приводить к crash или ложному success state.

### Связь с лояльностью

1. Список доступных icon names будет получать `effectiveContentAccess`: VPN-active или куплена нужная иконка.
2. Если VPN окончательно утрачивается, а выбранная иконка не куплена за токены, Android показывает обязательное объяснение с действием `Перезапустить и вернуть базовую иконку`. Затем запускается тот же прозрачный restart flow; на iOS применяется доступная иконка обычным iOS flow без Android Alert.
3. До подтверждения перезапуска контент уже блокируется, но текущая launcher-иконка может оставаться видимой только до следующего обязательного применения. Это необходимо, чтобы не обходить ранее согласованный честный Android Alert.

### Приёмка

- После подтверждения в Android launcher ровно один enabled alias.
- Отмена не создаёт alias и не меняет иконку.
- Все альтернативы и возврат базовой иконки проверены на Pixel_7a.
- На iOS прежняя смена иконки не регрессировала после Android-патча.

## Этап 4. Yandex Mobile Ads на Android

Официальные ориентиры: [React Native SDK 8 — интеграция](https://ads.yandex.com/helpcenter/ru/dev/react-native/quick-start), [adaptive inline banner](https://ads.yandex.com/helpcenter/ru/dev/react-native/adaptive-inline-banner), [adaptive sticky banner](https://ads.yandex.com/helpcenter/ru/dev/react-native/adaptive-sticky-banner), [rewarded ad](https://ads.yandex.com/helpcenter/ru/dev/react-native/rewarded) и [GDPR consent](https://ads.yandex.com/helpcenter/ru/dev/react-native/gdpr).

### Secrets и demo/prod режим

В реальном `src/config/Secrets.ts` подготовить форму:

```ts
export const YANDEX_AD_UNIT_IDS = {
  android: {
    inlineBanner: '',
    stickyBanner: '',
    rewarded: '',
  },
  ios: {
    inlineBanner: '',
    stickyBanner: '',
    rewarded: '',
  },
} as const;
```

1. В `__DEV__` и до создания production IDs сервис возвращает только `demo-banner-yandex` для обоих баннеров и `demo-rewarded-yandex` для reward.
2. В release build отсутствие production ID должно отключить соответствующий слот с понятной developer warning, а не отправить пустой запрос SDK.
3. `Secrets.example.ts` включает ту же структуру, но не реальных ID.

### Android native и consent

1. Установить пакет, выполнить autolinking, затем clean debug build на Pixel_7a.
2. Проверить manifest merger и наличие/политику `com.google.android.gms.permission.AD_ID`. Не удалять AD_ID без подтверждённой продуктовой политики; при удалении явно зафиксировать возможное снижение релевантности рекламы.
3. Перед единственным `MobileAds.initialize()` передавать сохранённый consent. Для GDPR-региона показать диалог, сохранить выбор и при каждом запуске вновь передать `MobileAds.setUserConsent(...)` до SDK init.
4. Не включать COPPA/age-restricted флаг без отдельного юридического решения: приложение рассчитано на студентов, но это не равнозначно детскому приложению.
5. Проверить Android logcat по `Yandex Ads`/`YandexAds` для подтверждения SDK, banner и rewarded integration.

### Общие компоненты

1. `AdsProvider` — единственная точка решения `adsEnabled`; никакой экран не запрашивает рекламу напрямую, не проверив entitlement.
2. `InlineBannerAd`:

   - использует `BannerAdSize.inlineSize(availableWidth, maxHeight)`;
   - учитывает padding/safe area;
   - показывает контейнер только после загрузки;
   - при `onAdFailedToLoad` скрывается без бесконечного retry.

3. `StickyBannerAd`:

   - использует `BannerAdSize.stickySize(availableWidth)`;
   - получает выделенное место в layout, не перекрывает bottom tabs, header, CTA и safe area;
   - не рендерит более одного sticky одновременно.

4. `RewardedAdService`:

   - создаёт один `RewardedAdLoader`;
   - предзагружает не более одного объявления рядом с доступной CTA;
   - запускает `show()` только после нажатия пользователя;
   - ведёт lifecycle `loaded → shown → rewarded/dismissed/failed`;
   - начисляет токены ровно один раз на конкретный показ и только из `onRewarded`;
   - ограничивает retry и после ошибки не зацикливает запросы.

### Точные места размещения

| Формат | Экран / slot | Ограничение |
| --- | --- | --- |
| Sticky | `LoadingScreen` после успешного login/2FA и до полной готовности данных | Показывается только если ad gate уже разрешает рекламу; безопасная зона и нижняя граница зарезервированы. |
| Sticky | Низ `SkippedClassesScreen` («Пропущенные занятия») | Включён в v2.4.0; зарезервировать высоту в scroll/list footer, не перекрывать последнюю карточку, кнопки и safe area. |
| Inline | Главный экран БАРС, footer после дисциплин | Footer списка, не внутри item и не перед ключевой информацией. |
| Inline | Боковой Drawer, после всех разделов | В `DrawerContentScrollView`, ниже навигации/выхода и без влияния на счётчики пунктов. |
| Inline | Расписание, только footer выбранного сегодняшнего дня после занятий | Не показывать при поиске чужого расписания, в пустом дне или если выбран не сегодняшний день. |
| Rewarded | Экран «Лояльность» в «Прочем» | Явная кнопка, состояние загрузки и остаток дневных просмотров. |

Все ad-компоненты скрыты при active VPN и при локально купленном постоянном отключении рекламы. Пользователь с VPN не видит rewarded CTA, поскольку это также рекламный формат.

## Этап 5. Лояльность, токены и unlocks

### Хранение и модель данных

Создать `LoyaltyService` / `LoyaltyProvider` с отдельным storage façade поверх MMKV. Это не должно быть частью BARS credentials и не должно случайно удаляться `ClearStorage`.

Минимальное persistent-состояние:

```ts
type LoyaltyState = {
  balance: number;
  lastLoginRewardDay?: string;
  rewardedDay?: string;
  rewardedViewsToday: number;
  unlockedIconIds: string[];
  lightThemeUnlocked: boolean;
  adsRemovalUnlocked: boolean;
};
```

1. Календарный день рассчитывается по локальной дате устройства и хранится в формате `YYYY-MM-DD`.
2. При смене дня `rewardedViewsToday` сбрасывается до 0. Изменение времени устройства не может надёжно защищаться без сервера; это допустимо только пока токены не имеют денежной/cross-device ценности.
3. Все операции начисления/траты выполняются синхронно/атомарно в одном сервисе, с проверкой отрицательного баланса и повторного callback.
4. Инъецировать генератор случайного числа в reward calculation, чтобы тесты могли проверять диапазон детерминированно.

### Экономика rewarded

| Номер успешного rewarded callback за день | Начисление |
| --- | --- |
| 1 | 10 токенов |
| 2 | 6 токенов |
| 3 | случайно от 2 до 5 включительно |
| 4 | случайно от 2 до 5 включительно |
| 5 | случайно от 2 до 5 включительно |
| 6 и далее | CTA disabled, реклама не запрашивается |

1. Индекс определяется по количеству уже успешно выданных наград, а не по числу нажатий/показов/ошибок.
2. `onAdDismissed`, `onAdFailedToShow`, закрытие до callback и ошибка загрузки не расходуют лимит и не начисляют токены.
3. UI показывает доступное число rewarded просмотров (`0/5` … `5/5`) и ясный текст следующей награды или диапазона.

### Награда за вход

За первый успешный вход в приложение начисляется **ровно 1 токен за локальный календарный день**, а не за каждое закрытие/открытие. Ключ `lastLoginRewardDay` записывается в той же атомарной операции, что и баланс.

Награда за вход начисляется и активному VPN-клиенту в реальный баланс; на экране всё равно отображается `∞`, пока VPN активен.

### Unlock catalogue

1. Базовыми бесплатными остаются безопасная стартовая иконка `cool` и тёмная тема.
2. `LoyaltyCatalog` описывает только продуктовые правила: id, тип (icon/theme/ad-free), цена, title, доступность. Каталог v2.4.0 фиксирован:

   | Item | Цена |
   | --- | ---: |
   | Светлая тема | 35 токенов |
   | Иконка `dragons` | 25 токенов |
   | Иконка `simple` | 50 токенов |
   | Иконка `matterial` | 75 токенов |
   | Иконки `gold`, `crymat`, `crysign` | по 100 токенов |
   | Постоянное отключение рекламы | 450 токенов |

3. Альтернативные иконки и светлая тема открываются после покупки соответствующего item.
4. `adsRemovalUnlocked` — локальная **постоянная** покупка за 450 токенов; после неё реклама не возвращается при утрате VPN и не имеет срока действия.
5. При недостаточном балансе покупка не проходит; UI показывает требуемую стоимость и доступный баланс.
6. Лояльность локальна для устройства и не защищена от root/backup. До появления реальной оплаты, синхронизации или ценных преимуществ сервер лояльности не нужен; после появления — клиентский баланс необходимо заменить серверным.

### Глобальный индикатор и экран управления

1. Добавить `TokenBalanceBadge` в общий слой `AppEntry`/Paper Portal, а не копировать его на каждый экран. Он отображается в правом верхнем углу с учётом safe area и не зависит от tab/Drawer/stack; перед числом/знаком бесконечности используется MaterialIcons `loyalty`.
2. Badge доступен и в guest navigation, и после входа; он не должен перекрывать кнопки header или QR controls. В camera-режиме расположение проверяется вручную на Android.
3. При VPN-active badge отображает значок бесконечности вместо числа, но не изменяет `balance`.
4. В «Прочем» добавить отдельный экран «Лояльность»: баланс, rewarded CTA, дневной прогресс, каталог unlocks и статус ad-free.
5. Во всех пользовательских navigator-ах, tab/drawer labels и screen header-ах переименовать «Настройки» в «Прочее» и заменить значок раздела на MaterialIcons `miscellaneous-services`. Внутреннее техническое имя `SettingsStack` можно сохранить, чтобы не расширять миграцию navigation.

1. VPN-active временно открывает все альтернативные иконки, светлую тему и ad-free без траты токенов.
2. После срабатывания правил окончательной потери VPN пересчитать доступ к каждому item по `locallyPurchasedUnlock`.
3. Если светлая тема не куплена — немедленно переключить на бесплатную тёмную тему.
4. Если текущая иконка не куплена — применить Android/iOS fallback flow из этапа 3.
5. Если `adsRemovalUnlocked` куплен за 450, реклама не возвращается даже при потере VPN. Если не куплен — возвращается согласно `adsEnabled`.
6. Ничего из реального баланса, дневного лимита или перечня купленных unlocks не сбрасывается при изменении VPN-статуса.

## Этап 6. DragoNet: HTTPS proxy, демо-доступ, политика проверок и карточка в «Прочем»

### Отдельный серверный проект

В корне репозитория создать автономную папку `vpn-subscription-proxy/` без превращения основного RN-проекта в monorepo.

```text
vpn-subscription-proxy/
├─ src/
│  ├─ server.ts
│  ├─ startupDiscovery.ts
│  ├─ requestGate.ts
│  ├─ vpnPanelClient.ts
│  ├─ verifySubscription.ts
│  ├─ createDemoAccess.ts
│  ├─ demoCooldownStore.ts
│  └─ schema.ts
├─ test/
├─ package.json
├─ tsconfig.json
├─ .env.example
├─ README.md
├─ deploy/
│  └─ dragonet-subscription-proxy.service
└─ Dockerfile                 # только если выбран Docker deployment
```

Технология — минимальный TypeScript HTTPS/Fastify-сервис на Node 24 с schema validation, timeout и unit-тестами. TLS завершается самим proxy: это необходимо для обязательного discovery TLS-пары при каждом старте. Runtime-хранилище cooldown размещается вне репозитория, например в `/var/lib/dragonet-subscription-proxy/`.

### Startup discovery: public IP, домен и TLS-пара

До открытия публичного HTTPS listener proxy **при каждом запуске процесса** строит runtime-identity. Значения не берутся из mobile приложения и не кэшируются между перезапусками.

1. Параллельно запросить внешний IPv4 у трёх независимых HTTPS-сервисов: `https://api.ipify.org`, `https://ifconfig.me/ip` и `https://icanhazip.com`. Для каждого действуют короткий timeout, нормализация и проверка, что результат — глобальный IPv4, а не loopback/private/link-local/служебный адрес.
2. Использовать результат только при голосовании не менее двух сервисов за один и тот же IP. При отсутствии кворума proxy fail-closed: не поднимает публичный listener и завершает процесс с безопасной диагностикой без ключей/Token.
3. Сначала просмотреть только пары `fullchain.pem` + `privkey.pem` в каталогах `/etc/letsencrypt/live/*/` (с разворачиванием symlink через `realpath`). Для каждой пары проверить читаемость, криптографическое соответствие certificate/private key, срок действия сертификата и извлечь DNS-имена из SAN, затем CN.
4. Домен считается обнаруженным только если одно из точных DNS-имён сертификата при DNS-resolve даёт IP из шага 2. Wildcard сам по себе не является достаточным именем: нужен конкретный SAN/CN, совпадающий с DNS. При нескольких подходящих именах выбрать детерминированно в пределах приоритетной пары и использовать его как ожидаемый SNI/Host.
5. Лишь если в `/etc/letsencrypt/live/` не найдено ни одной валидной пары с доменом, соответствующим IP, проверить конечный allow-list популярных мест: `/etc/ssl/{fullchain.pem,privkey.pem}`, `/etc/nginx/ssl/{fullchain.pem,privkey.pem}`, `/opt/*/ssl/{fullchain.pem,privkey.pem}`, `/root/{fullchain.pem,privkey.pem}`, `/root/{cert.pem,key.pem}` и одноуровневые пары ACME в `/root/.acme.sh/`. Рекурсивно сканировать весь диск или `/root` нельзя.
6. Proxy использует выбранные домен и TLS-пару для своего HTTPS listener, строгой проверки `Host`/SNI и построения `demoSubURL`. Если на старте нет одновременно кворума IP, подходящего домена и валидной TLS-пары, сервис не отвечает извне. После продления сертификата deployment hook перезапускает сервис, что повторяет discovery.

### Контракт proxy

```text
POST <PROXY_REQUEST_PATH>
Content-Type: application/json
Mpei-App-Req-Id: DragoNet-DD-MM-YYYY-DEVICE_STRING

body: { "purpose": "verify", "clientName": "[@DragoNetworkBot]_ENG_@AAD_902_987135996_BmK" }
   or { "purpose": "demo" }
```

1. `purpose` — строгое discriminated union: `verify` требует нормализованный `clientName`, а `demo` не принимает имя клиента. Полный URL персональной подписки в verify не передаётся.
2. Каждый запрос к публичному listener до body parsing проходит `Mpei-App-Req-Id` gate. Допустим только вид `DragoNet-DD-MM-YYYY-DEVICE_STRING`: все три числовые части — текущая дата в зоне `Europe/Moscow`, с нулевым заполнением. Это фиксирует значение `DD`, присутствующее в заданном формате, наряду с текущими месяцем и годом.
3. `DEVICE_STRING` — весь непустой остаток после четвёртого дефиса. Он не имеет whitelist-формата и принимается как любая корректная HTTP header value без управляющих символов; proxy не пытается разобрать его как серийный номер.
4. Если заголовок отсутствует, не проходит формат или дата неактуальна, proxy **не отправляет HTTP-ответ вообще**: raw socket закрывается до маршрутизации, JSON parsing, rate limit и логирования. Нельзя заменять это на `401`/`400`, HTML или JSON. Локальный `/healthz` является отдельным loopback-only check и не открывается на публичном listener.
5. Для валидного заголовка proxy валидирует schema/длину имени, применяет rate limit, timeout и краткий cache по HMAC имени только для `verify`. Кэш никогда не используется для `demo`.
6. Единственный контрактный JSON-ответ для запросов, прошедших gate, использует следующие поля; отсутствующие в сценарии поля не сериализуются:

   | Сценарий | Ответ |
   | --- | --- |
   | Проверка: клиент найден и активен | `{ "reqStatus": "success", "isClientFound": true, "isClientActive": true }` |
   | Проверка: клиент найден, но не активен | `{ "reqStatus": "success", "isClientFound": true, "isClientActive": false }` |
   | Проверка: клиента нет | `{ "reqStatus": "success", "isClientFound": false, "isClientActive": false }` |
   | Демо успешно создано | `{ "reqStatus": "success", "demoSubURL": "https://…" }` |
   | Валидный запрос, который нельзя выполнить (cooldown, rate limit, upstream/schema failure) | `{ "reqStatus": "failed" }` |

7. `reqStatus` имеет только значения `"success"` и `"failed"`. `isClientFound` и `isClientActive` есть только в успешной verify-ветке; `demoSubURL` — только в успешной demo-ветке. Причину отказа, panel details, списки клиентов, Token, TLS-пути и raw device/IP не отдавать.
8. В verify-ветке proxy выполняет `GET {VPN_PANEL_BASE_URL}/apiv2/clients` c заголовками `Token` и `Accept: application/json`. `isClientFound` определяется точным равенством `client.name === clientName`; `isClientActive` — найденным клиентом с `client.enable === true`, как в текущей политике панели.

9. CORS не считать защитой: мобильный клиент не является браузером. Формат `Mpei-App-Req-Id` — фильтр трафика, а не криптографическая аутентификация; поэтому остаются обязательными узкие schema, timeout, rate limit, закрытие invalid-header socket, cooldown демо и минимальный ответ. Позднее этот gate можно дополнить Play Integrity/App Attest.

### Демо-доступ через VPN panel

1. Demo-ветка после успешного request gate создаёт клиента тем же S-UI API, который использует Telegram-бот: `POST /apiv2/save` c `object: "clients"`, `action: "new"` и сериализованным `data`.
2. Имя строится без запроса к списку клиентов: `MpeiApp-demo-DD-MM-YYYY-XXXXX`, где дата — текущая `Europe/Moscow`, а `XXXXX` — пять криптографически случайных заглавных латинских букв/цифр. Коллизии имени, password и UUID заранее не проверяются.
3. По референсу из бота payload использует активные demo inbounds из server configuration, группу `Dragon's clients`, `enable: true`, 5 GiB трафика, expiry через 1 сутки, `delayStart: false`, `autoReset: true`, `resetDays: 1`, нулевые счётчики и описание `demo access via MpeiApp`.
4. Поле `config` повторяет совместимую с S-UI форму бота для `trojan`, `anytls`, `hysteria2`, `tuic` и `vless`: для каждого протокола задаётся имя клиента; password/UUID генерируются криптографически случайно, не сравниваются с существующими и не сохраняются в proxy database или логах.
5. После успешного сохранения proxy строит `demoSubURL` из обнаруженного домена, настроенных panel subscription port/path prefix и percent-encoded имени клиента. Ссылка возвращается только в ответе на тот запрос, который создал клиента; в логи она не попадает.

### Cooldown демо-доступа

1. Proxy хранит runtime SQLite-базу с двумя независимыми типами записей: `ip` и `device`. В каждой записи — `identityType`, HMAC-SHA-256 нормализованного значения с server-side `DEMO_COOLDOWN_HMAC_KEY`, `issuedAt`, `expiresAt` и технический статус reservation/issued. Raw IP и raw `DEVICE_STRING` не сохраняются.
2. IP берётся из фактического remote socket address и нормализуется; `X-Forwarded-For` игнорируется, кроме явно сконфигурированного перечня trusted reverse-proxy адресов. Значение device — принятый остаток `DEVICE_STRING` без попытки интерпретации.
3. Перед созданием клиента атомарно зарезервировать обе identity. Любое действующее совпадение **либо** по IP, **либо** по device отклоняет demo-ветку с `{ "reqStatus": "failed" }`; значения не проверяются только парой и причина отказа не раскрывается.
4. При успешном panel create обе reservation фиксируются как issued; при известной ошибке создания освобождаются. Незавершённая после аварии reservation остаётся консервативно блокирующей до истечения срока, чтобы не создать повторное демо из-за гонки/restart.
5. `expiresAt` равен моменту выдачи плюс **один календарный месяц** в зоне `Europe/Moscow`; expired records регулярно удаляются. Поэтому тот же IP или тот же `DEVICE_STRING` может получить новый demo лишь после завершения этого месяца, независимо от второго значения.

### Конфигурация и развёртывание на Debian 11

1. В root-owned systemd `EnvironmentFile`/proxy `.env` вне Git хранить:

   - `VPN_PANEL_BASE_URL`;
   - `VPN_PANEL_TOKEN`;
   - `VPN_DEMO_INBOUNDS` (явный список/JSON активных inbounds для создаваемого demo-клиента);
   - `VPN_SUBSCRIPTION_PORT` и `VPN_SUBSCRIPTION_PATH_PREFIX` для построения `demoSubURL`;
   - `PROXY_REQUEST_PATH`, совпадающий с path из мобильного `Secrets.ts`;
   - `DEMO_COOLDOWN_HMAC_KEY`;
   - `HTTPS_PORT=443`, путь runtime state directory и настройки локального health check;
   - cache/rate-limit/timeout values;
   - при необходимости trusted proxy setting.

   Домен и certificate/key paths в production env не дублировать: их источником служит обязательный startup discovery. Panel URL/Token, HMAC key, пароли и UUID никогда не добавляются в приложение.

2. На стороне MpeiApp в реальном `src/config/Secrets.ts` и в `Secrets.example.ts` завести две отдельные публичные константы вместо единого полного URL:

   ```ts
   export const DRAGONET_PROXY_DOMAIN = ''; // только DNS host, без scheme/path
   export const DRAGONET_PROXY_PATH = '';   // начинается с /
   ```

   Мобильный transport строит endpoint исключительно как `https://` + `DRAGONET_PROXY_DOMAIN` + `DRAGONET_PROXY_PATH`, валидирует обе части до запроса и не содержит panel credentials. Перед релизом значение домена сверяется с доменом, который proxy обнаружит из TLS-пары; path должен совпадать с `PROXY_REQUEST_PATH`.

3. README должен содержать пошаговый Debian 11 deployment:

   - установить Node 24 и системные build prerequisites;
   - создать непривилегированного пользователя сервиса;
   - создать закрытый state directory для SQLite и скопировать проект/выполнить production install/build;
   - разместить EnvironmentFile с правами `root:root 600`, чтобы его прочитал systemd, но он не оказался в Git;
   - предоставить service user только read access к реальным certificate/key файлам, на которые указывают symlink Certbot, и `CAP_NET_BIND_SERVICE` для 443;
   - получить/обновлять TLS сертификат через Certbot и добавить deploy-hook `systemctl restart dragonet-subscription-proxy`;
   - установить systemd unit, `daemon-reload`, enable/start/status;
   - открыть только требуемые порты firewall;
   - проверить с loopback `/healthz`, корректный POST verify и отсутствие HTTP-ответа при POST без/с неверным `Mpei-App-Req-Id`, не выводя Token;
   - описать обновление/rollback и просмотр безопасных журналов.

4. Nginx не завершает TLS для этого сервиса: proxy сам читает найденную TLS-пару и слушает HTTPS. Если существующий Nginx уже занимает 443 на том же IP, до deployment нужно освободить порт либо выделить proxy отдельный IP/домен; скрытый reverse proxy с TLS termination не удовлетворяет этому требованию. Внешний доступ приложения к panel API `/apiv2/*` не открывается.

### Мобильный VPN-сервис и request ID

1. Добавить один transport для обоих запросов proxy. Он строит URL только из `DRAGONET_PROXY_DOMAIN` и `DRAGONET_PROXY_PATH`, передаёт JSON `{ purpose: "verify", clientName }` либо `{ purpose: "demo" }` и на **каждый** POST добавляет `Mpei-App-Req-Id`.
2. `Mpei-App-Req-Id` строится в форме `DragoNet-DD-MM-YYYY-DEVICE_STRING`. Дату формировать через `Intl.DateTimeFormat` в `Europe/Moscow`, чтобы она совпадала с proxy gate. Для `DEVICE_STRING` сначала неблокирующе попытаться получить доступный серийный номер устройства; если API/платформа/permission возвращают пустое, placeholder или ошибку, использовать строку с названием и версией ОС и моделью устройства. Не добавлять ради serial новые опасные runtime permissions; fallback является штатным вариантом для iOS и современных Android.
3. Создать чистую `extractVpnClientName(link)`:

   - принимает subscription URL вида `https://dragonservices.online:21056/dragonet/connect/<name>`;
   - требует HTTPS, разрешённый origin и заданный path prefix;
   - получает последний непустой path segment;
   - применяет `decodeURIComponent` ровно один раз;
   - не меняет case, `[]`, `@`, `_` и прочие значимые символы;
   - отклоняет чужой host, неверный path, пустое имя, не-URL и слишком длинную строку.

4. Создать `VpnSubscriptionService` с разделёнными результатами: `ACTIVE`, `INACTIVE_CONFIRMED`, `TRANSIENT_FAILURE`, `OFFLINE_SKIPPED`. `reqStatus: "success"` с `isClientActive: true` даёт `ACTIVE`; `reqStatus: "success"` с `isClientActive: false` — `INACTIVE_CONFIRMED`; `reqStatus: "failed"`, timeout, закрытие socket из-за invalid header и malformed response — `TRANSIENT_FAILURE`.
5. Хранить только нормализованное имя, timestamp и counters. Не хранить персональную URL-ссылку, `demoSubURL`, список клиентов, Device String или Token. При новой ссылке не перезаписывать сохранённое активное имя до успешного подтверждения новой; пользователь может отдельно выбрать «Отключить подписку на этом устройстве».
6. Успешный demo-ответ не подменяет сохранённую платную подписку и не выдаёт локальный VPN entitlement сам по себе. `demoSubURL` живёт лишь в состоянии result sheet: пользователь может явно скопировать или открыть её в установленном VPN-клиенте, после чего покупает полноценную подписку через Telegram.

### Точная политика перепроверок и отзыва доступа

Persistent-состояние дополнить:

```ts
type VpnVerificationState = {
  clientName?: string;
  lastVerifiedAt?: string;
  technicalFailureStreak: number;
  firstTechnicalFailureAt?: string;
  inactiveStreak: number;
  firstInactiveAt?: string;
  lastEffectiveStatus: 'ACTIVE' | 'GRACE' | 'REVOKED' | 'NONE';
};
```

Правила обработки одного запроса:

| Результат proxy/сети | Что сохранить | Влияние на доступ |
| --- | --- | --- |
| `ACTIVE` | Обнулить обе streak, обновить `lastVerifiedAt`, отметить `ACTIVE` | VPN entitlement включён. |
| `INACTIVE_CONFIRMED` | Обнулить technical streak; увеличить `inactiveStreak`, задать `firstInactiveAt` только в начале streak | До условия C статус остаётся grace/active; после условия C VPN entitlement отзывается. |
| `TRANSIENT_FAILURE` (timeout, 5xx, malformed) | Увеличить technical streak, задать `firstTechnicalFailureAt` в начале; сбросить `inactiveStreak`, так как последовательность «нет подписки» прервана | До условий A/B сохраняется grace/предыдущий доступ; после A/B VPN entitlement отзывается. |
| `OFFLINE_SKIPPED` | Не менять ни один counter/streak/timestamp попытки | Текущий effective status сохраняется. |

VPN entitlement отзывается **только** если выполняется хотя бы одно условие:

1. `technicalFailureStreak >= 10`;
2. `technicalFailureStreak >= 3` и с первого технического сбоя этой последовательности прошло не меньше 7 суток;
3. `inactiveStreak >= 3` и с первого подтверждённого ответа «нет активной подписки» прошло не меньше 3 суток.

Дополнительные правила:

1. Автоматическая проверка запускается один раз последним шагом успешной online data chain БАРС. Ручная «Проверить снова» в «Прочем» тоже учитывается в той же последовательности результатов.
2. `reqStatus: "failed"`, schema error, закрытый proxy socket из-за некорректного request ID и невалидный ответ proxy — это `TRANSIENT_FAILURE`, а не доказательство отключённой подписки.
3. `ACTIVE` всегда возвращает полный VPN access и обнуляет обоe состояния неопределённости.
4. При отсутствии сохранённого имени `vpnActive = false`; рекламный/токенный доступ определяется только локальными покупками.
5. После последнего порога отзыва реклама возвращается только если не куплен `adsRemovalUnlocked`; темы/иконки — только если не куплены соответствующие items.

## Зафиксированные предпосылки deployment

Все продуктовые решения перед кодом закрыты. Перед production deployment оператор подставляет фактические публичные `DRAGONET_PROXY_DOMAIN` и `DRAGONET_PROXY_PATH` в игнорируемый `Secrets.ts` и одинаковый path в EnvironmentFile proxy. Startup discovery не заменяет эти константы в уже собранном APK: он проверяет, что опубликованный домен действительно соответствует публичному IP и доступной TLS-паре VPS, и fail-closed останавливает сервис при расхождении.
