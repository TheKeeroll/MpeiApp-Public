# Технический план обновления MpeiApp до v2.5.0

## Статус, границы и ветки

Статус: **этапы 0–4 выполнены; этапы 5–7 не начаты**.

Исходная точка — выпущенная v2.4.0. Этот документ переносит все явно отложенные
части предыдущего плана и добавляет согласованные задачи v2.5.0. Он не является
разрешением на изменение исходников, зависимостей, секретов, сервера или
удалённого Git-репозитория.

Рабочая модель Git для этой версии:

| Назначение | Ветка |
| --- | --- |
| Повседневная разработка и CI | dev |
| Проверенный релизный срез | v2 |
| Историческая стабильная ветка без новых изменений | main |

До релиза изменения разрабатываются в dev. После приёмки ровно проверенный
релизный коммит переносится в v2. main не является целью обычных коммитов или
автоматического merge.

## Состав v2.5.0

### Новые задачи

1. Отдельное состояние успешной аутентификации без найденного Личного кабинета
   студента вместо ошибочного LOGIN_FAIL.
2. Переработанная справка на экране входа с разворачиваемыми блоками.
3. Быстрый показ навигации после минимально необходимой загрузки БАРС.
4. Анимированные этапы на LoadingScreen для всех сценариев загрузки.
5. Отдельный идентификатор Yandex Ads для каждого inline/sticky-размещения,
   новые баннеры гостевого расписания, зачётной книжки и стипендий.
6. Полная интеграция DragoNet: proxy, проверка подписки, demo-доступ, карточка
   в «Прочем» и инструкции по импорту demo-подписки.

### Перенесённое из плана v2.4.0

1. Автономный защищённый DragoNet HTTPS proxy и его deployment-документация.
2. Мобильный сервис проверки подписки, политика grace/revoke и связь с
   рекламой/лояльностью.
3. Минимальные критические unit/component/integration-тесты без массовых
   snapshot-тестов.
4. GitHub Actions для качества TypeScript, Metro, Android debug APK и proxy.
5. Безопасное materialization Google Services JSON в CI только при
   необходимости debug-сборки; без release keystore, VPN Token и production
   advertising IDs.

## Зафиксированные решения

- Время, относящееся к БАРС и DragoNet, вычисляется в зоне Europe/Moscow.
- Полные персональные ссылки DragoNet, demoSubURL, Token панели, raw IP,
  Device String, TLS-ключи и production ad IDs не попадают в Git, логи,
  аналитические события или persistent storage приложения.
- Для копирования demo-ссылки используется уже установленный
  @react-native-clipboard/clipboard; новую зависимость для этого не добавлять.
- Ссылки на регистрацию БАРС, App Store и APK не показываются пользователю
  текстом: вместо них отображаются кнопки, открывающие URL через Linking.
- Android реализуется и принимается первым. iOS проходит отдельную сборку и
  ручную приёмку после Android gate.
- Демонстрационные Yandex IDs остаются в debug. В release не настроенный
  placement получает demo ID, а не пустой запрос.

## Этап 1. Состояние STUDENTS_NOT_FOUND и экран входа

### Целевое состояние

В LoginState добавить отдельное состояние STUDENTS_NOT_FOUND. Это состояние
аутентифицированного пользователя с ещё не подготовленным Личным кабинетом, а
не BARSError и не вариант LOGIN_FAIL.

~~~text
логин/пароль → NEED_2FA → код 2ФА принят → получение студента
                                            ├─ студент получен → ONLINE
                                            └─ ошибка до студента
                                               ├─ январь/февраль/август/сентябрь
                                               │  → STUDENTS_NOT_FOUND
                                               └─ иной месяц → обычная ошибка входа
~~~

### Точная граница классификации

1. В BARS.ts явно отслеживать фазу одной первичной попытки: ожидание 2ФА,
   код принят, основные данные студента получены. Не определять сценарий по
   тексту исключения вроде split of undefined.
2. Кандидатом на STUDENTS_NOT_FOUND является **любая** ошибка в первичной
   online-цепочке после того, как сервер принял код второго фактора, и до
   установки mCurrentData.student/доступных семестров. В частности это
   включает ошибку redirect, multi-account route, ответ главной страницы,
   parser student info и неожиданный ответ БАРС.
3. Неверный/запрещённый код 2ФА, ошибка отправки кода, отсутствие сети до
   принятия кода, неверный логин/пароль, offline fallback, session restore
   при Init(..., false), test mode и ошибки после получения student data не
   классифицируются как STUDENTS_NOT_FOUND.
4. Проверять только месяцы 1, 2, 8 и 9 в Europe/Moscow. Функция получения
   месяца должна принимать дату/clock как параметр в тестах, а не зависеть
   напрямую от текущего момента.
5. Login2FA не должен преждевременно превращать post-2FA исключение в
   LOGIN_FAIL. Для ожидаемого сценария он возвращает типизированный outcome,
   который верхний auth flow переводит в LoginState.
6. Когда студент уже получен, любой последующий сбой остаётся обычной
   частичной ошибкой загрузки данных; состояние входа не откатывается.

### Данные и повторная попытка

1. При переходе в STUDENTS_NOT_FOUND сохранить введённые credentials в
   STORAGE_KEYS.CREDENTIALS и в памяти BARSAPI. Удалить stale student cache и
   данные БАРС, относящиеся к прежнему пользователю, чтобы чужой офлайн-срез не
   оказался доступен после новой попытки. Общие настройки оформления, consent и
   отдельное хранилище лояльности не затрагивать.
2. Вынести целевой метод повторной попытки, например
   RetryStudentAccountCheck(): он берёт сохранённые credentials, показывает
   AUTHENTICATED_LOADING_DATA, снова проходит normal login/2FA flow и только
   после получения студента выходит в обычную загрузку.
3. «Выйти из аккаунта» использует тот же осознанный logout path, что и
   Drawer: удаляет credentials, temporary 2FA code и данные БАРС, сбрасывает
   LoginState в NOT_LOGGED_IN. Никакой пароль не логируется.
4. При logout/new-login увеличить session generation. Все незавершённые
   загрузки и post-login задачи сверяют этот generation перед dispatch,
   записью в MMKV и переходом состояния.

### UI

1. App.tsx и LoginScreenWrapper отображают STUDENTS_NOT_FOUND как часть
   экрана входа, без полей ввода логина/пароля и без Alert «Ошибка входа».
2. Показать сохранённый логин и маскированный пароль. Для пароля длиной от 3
   символов используется первый символ + нужное число звёздочек + последний;
   для длины 1–2 не раскрывать больше, чем требует правило первого/последнего
   символа. Значение не делать копируемым и не передавать в accessibility
   label целиком.
3. Основной текст:

   > Вход в аккаунт БАРС выполнен, но не найдено ни одного Личного Кабинета
   > студента. Если вы недавно поступили в МЭИ, то это нормально — вуз ещё не
   > успел всё подготовить, просто пробуйте снова через несколько дней. Если
   > проблема сохранится дольше пары недель — свяжитесь с разработчиком.

4. Под текстом разместить две явные кнопки: «Выйти из аккаунта» и
   «Проверить снова». На повторной проверке кнопка блокируется до завершения
   попытки; экран загрузки получает свой этап.
5. Проверить как интерактивный вход, так и автологин с сохранённым временным
   кодом 2ФА: они не должны обходить новую границу состояния.

### Приёмка этапа

- В разрешённых месяцах все post-2FA ошибки до student data показывают
  специальный экран и сохраняют credentials.
- В остальных месяцах те же ошибки остаются обычной ошибкой входа.
- При существующем student data состояние STUDENTS_NOT_FOUND недостижимо.
- «Проверить снова» корректно проходит 2ФА при необходимости; logout возвращает
  стандартную форму входа без старых данных.

### Результат выполнения этапа 1 (03.09.2026)

- `STUDENTS_NOT_FOUND` стал отдельным `LoginState` и типизированным outcome, а
  не `BARSError`. Он возникает только для первичной online-попытки после
  успешного принятия кода 2ФА и до сохранения данных студента, в разрешённые
  месяцы Europe/Moscow.
- Добавлены generation-токены входа/загрузки: устаревшая попытка, ответ 2ФА
  или post-login задача не переводят приложение обратно в старое состояние.
- При специальном состоянии credentials сохраняются, а кэш и Redux-данные
  БАРС очищаются. Обычный logout из Drawer использует тот же путь и не удаляет
  тему, consent или состояние лояльности.
- Экран входа показывает сохранённый логин, невыделяемую маску пароля,
  объяснение и действия «Проверить снова» / «Выйти из аккаунта».
- `yarn typecheck` выполнен успешно. Android-сборка по договорённости не

## Этап 3. Быстрая загрузка БАРС и прогресс на LoadingScreen

### Общий сервис этапов

1. Создать LoadingProgressService с изолированными сессиями. Каждая сессия
   имеет идентификатор, текущий этап и один предыдущий завершённый этап:

   ~~~ts
   type LoadingStageStatus = 'success' | 'failed'
   type LoadingProgress = {
     current?: {label: string}
     previous?: {label: string; status: LoadingStageStatus}
   }
   ~~~

2. API сервиса должен поддерживать start/advance/complete/fail/clear и
   игнорировать событие неактуальной сессии. Экран подписывается только на
   переданный progressKey; закрытие экрана очищает подписку, а не чужую
   сессию.
3. LoadingScreen получает progressKey и безопасный fallback label. Поэтому
   ни один существующий вызов LoadingScreen не остаётся полностью без текста.
4. Под Lottie-анимацией отрисовать:

   - текущий этап белым цветом, с плавным появлением снизу;
   - предыдущий этап выше, полупрозрачным;
   - к предыдущему добавлять «успешно» зелёным или «не удалось» красным.

   Для перехода использовать Animated/Reanimated, уже доступный проекту, без
   нового пакета. Быстрая смена нескольких этапов не должна ломать layout или
   показывать старую сессию.

### Покрытие всех существующих загрузок

| Сценарий | Минимальные этапы |
| --- | --- |
| Инициализация приложения | «Подготовка приложения...» |
| Ввод логина/пароля | «Проверка логина и пароля...», затем «Запрос к БАРС...» |
| Ввод и проверка 2ФА | «Проверка кода подтверждения...», затем «Получение основных данных студента...» |
| Основная online-загрузка | «Получение основных учебных данных...», затем «Подготовка основных разделов...»; внутри параллельно запрашиваются текущая неделя, оценки и долги |
| Фоновые разделы БАРС | конкретный этап при активном экране либо fallback «Загрузка раздела...» |
| Карта | «Загрузка карты...»; при fallback показать предыдущий результат корректно |
| Поиск расписания | «Поиск расписания...», «Загрузка занятий...» |
| Камера QR | «Подготовка камеры...» |

Для Books, Tasks, Reports, Orders, Questionnaires, RecordBook, Stipends,
SkippedClasses, Marks и обычного расписания необходимо передать хотя бы
fallback/конкретный progressKey. Ошибка конкретной операции получает красный
статус до перехода к обычному FetchFailed или Alert.

### Разделение core и background загрузки

1. Переписать LoadOnlineDataInternal из последовательной цепочки в два
   управляемых набора задач.
2. До перехода в LOGGED_IN запускать и ждать terminal state только для:

   - уже полученных основных данных студента и списка семестров;
   - текущих оценок;
   - долгов (запрос оценок прошлого семестра, если он существует);
   - текущей недели.

   Независимые core-запросы запускать параллельно через Promise.allSettled;
   зависимость «долги → доступный прошлый семестр» сохраняется. Сбой core
   раздела переводит его Redux slice в FAILED, но не держит приложение на
   бесконечном LoadingScreen после успешной аутентификации.

3. Сразу после завершения core-набора перейти в LOGGED_IN и показать
   навигацию/оценки. Это является границей UX, а не ожиданием всех данных.
4. После этой границы запускать ограниченную фоновую очередь (не
   неконтролируемый Promise.all, чтобы не перегружать БАРС) для:

   - личного расписания — **строго первым** заданием очереди: оно может
     загружаться долго и не должно задерживать вход или показ оценок;
   - фильтра доступных семестров;
   - почты;
   - пропусков;
   - зачётной книжки;
   - заданий;
   - отчётов;
   - стипендий;
   - приказов;
   - книг;
   - анкет;
   - DragoNet revalidation.

   Очередь фиксирует результат каждого раздела и не создаёт unhandled
   rejection. Пользователь может открыть раздел во время его загрузки и
   увидеть корректный LoadingScreen/FetchFailed.

5. Убрать общий модальный Alert о фоновой ошибке как побочный эффект долгой
   загрузки. Core-сбои отображаются у соответствующего раздела, а фоновый
   сбой не блокирует навигацию; безопасный диагностический лог остаётся.
6. Изменить контракт RegisterPostOnlineDataTask: задачи DragoNet запускаются

## Этап 5. DragoNet

### 5.1. Целевая схема и разграничение секретов

~~~text
MpeiApp
  ├─ VpnSubscriptionService
  │    ├─ verify: нормализованное имя клиента
  │    └─ demo: разовая ссылка только в result sheet
  └─ POST verify/demo + Mpei-App-Req-Id
                  ↓
DragoNet HTTPS proxy на VPS
  ├─ verify → VPN panel GET /apiv2/clients
  └─ demo   → VPN panel POST /apiv2/save
~~~

Мобильное приложение хранит только нормализованное имя клиента, timestamps и
счётчики policy. URL панели, Token, TLS private key, demo HMAC key, данные
клиентов и raw IP/device остаются исключительно на VPS.

Создать автономный проект vpn-subscription-proxy в корне репозитория, без
превращения React Native проекта в monorepo:

~~~text
vpn-subscription-proxy/
├─ src/
│  ├─ server.ts
│  ├─ startupDiscovery.ts
│  ├─ requestGate.ts
│  ├─ vpnPanelClient.ts
│  ├─ verifySubscription.ts
│  ├─ createDemoAccess.ts
│  ├─ demoCooldownStore.ts
│  └─ schema.ts
├─ test/
├─ package.json
├─ tsconfig.json
├─ .env.example
├─ README.md
└─ deploy/dragonet-subscription-proxy.service
~~~

Использовать небольшой TypeScript/Fastify HTTPS-сервис на Node 24 с schema
validation, timeout, rate limit и тестами. SQLite runtime state лежит вне Git,
например в /var/lib/dragonet-subscription-proxy.

### 5.2. Startup discovery и HTTPS listener

Перед открытием публичного listener при **каждом** запуске:

1. Параллельно запросить IPv4 у api.ipify.org, ifconfig.me/ip и icanhazip.com.
   Принять только нормализованный глобальный IPv4 при кворуме не менее 2 из 3;
   иначе fail-closed без публичного listener.
2. В первую очередь проверить пары fullchain.pem + privkey.pem в
   /etc/letsencrypt/live/*/, раскрыв symlink. Проверить читаемость, соответствие
   ключа сертификату, срок и SAN/CN.
3. Подходящим считать только конкретное DNS-имя сертификата, которое через DNS
   точно указывает на IP из голосования. Wildcard без конкретного имени
   недостаточен.
4. Только если Let’s Encrypt-пары не подошли, проверить ограниченный fallback
   allow-list: /etc/ssl, /etc/nginx/ssl, /opt/*/ssl, /root/{fullchain.pem,
   privkey.pem}, /root/{cert.pem,key.pem} и одноуровневые пары
   /root/.acme.sh. Не сканировать рекурсивно диск или /root.
5. Proxy сам завершает TLS, сверяет Host/SNI и строит demoSubURL. Nginx с TLS
   termination этому контракту не соответствует. При продлении сертификата
   Certbot deploy-hook перезапускает service и discovery повторяется.

### 5.3. Контракт proxy и request gate

~~~text
POST <PROXY_REQUEST_PATH>
Content-Type: application/json
Mpei-App-Req-Id: DragoNet-DD-MM-YYYY-DEVICE_STRING

{ "purpose": "verify", "clientName": "<normalised name>" }
{ "purpose": "demo" }
~~~

1. purpose — strict discriminated union. verify требует валидное
   нормализованное имя; demo не принимает имя. Полная личная ссылка никогда не
   отправляется для verify.
2. До parsing body gate принимает только заголовок с актуальными DD-MM-YYYY в
   Europe/Moscow и непустым остатком DEVICE_STRING без control characters.
3. При отсутствующем, неверном или просроченном заголовке закрыть raw socket
   **без HTTP-ответа**, маршрутизации, JSON parsing, rate limit и логирования.
   Публичного health endpoint нет; /healthz доступен только loopback.
4. Для валидного запроса применить schema/длину, timeout, rate limit и
   краткий cache по HMAC имени только в verify.
5. Единственные публичные JSON-ответы:

| Сценарий | Ответ |
| --- | --- |
| Найден активный клиент | { "reqStatus": "success", "isClientFound": true, "isClientActive": true } |
| Найден неактивный клиент | { "reqStatus": "success", "isClientFound": true, "isClientActive": false } |
| Клиента нет | { "reqStatus": "success", "isClientFound": false, "isClientActive": false } |
| Demo создано | { "reqStatus": "success", "demoSubURL": "https://…" } |
| Cooldown/rate-limit/upstream/schema error | { "reqStatus": "failed" } |

6. Причины отказа, panel response, Token, TLS-paths, raw IP/device и клиентское
   имя не попадают в ответ или журналы. Gate — только фильтр трафика, не
   криптографическая аутентификация; узкие schema/timeout/rate limit/cooldown
   остаются обязательными.
7. verify делает GET VPN_PANEL_BASE_URL/apiv2/clients с Token и Accept:
   application/json. Сопоставление — точное client.name === clientName;
   active означает найденный client.enable === true.

### 5.4. Demo и cooldown на сервере

1. После прохода gate demo вызывает S-UI API POST /apiv2/save с object clients,
   action new и сериализованным data, совместимым с текущим Telegram-ботом.
2. Имя: MpeiApp-demo-DD-MM-YYYY-XXXXX, где XXXXX — 5 криптографически
   случайных заглавных букв/цифр. Коллизии имени/password/UUID заранее не
   проверяются.
3. Payload использует настроенные активные demo inbounds, группу Dragon's
   clients, enable true, 5 GiB, expiry через 1 сутки, delayStart false,
   autoReset true, resetDays 1, нулевые счётчики и описание
   demo access via MpeiApp. Для trojan, anytls, hysteria2, tuic и vless
   повторить совместимую форму Telegram-бота; password/UUID генерировать
   криптографически и не сохранять.
4. Построить demoSubURL из обнаруженного домена, subscription port/path prefix
   и percent-encoded имени. Вернуть только создавшему запросу, не логировать.
5. SQLite cooldown имеет две независимые HMAC-SHA-256 записи: ip и device.
   Хранятся identityType, HMAC нормализованного значения, issuedAt, expiresAt
   и reservation/issued — без raw IP/device.
6. До создания атомарно зарезервировать обе identity. Совпадение либо IP,
   либо device отклоняет demo без раскрытия причины. При успехе reservation
   фиксируется, при известной ошибке panel освобождается; незавершённая после
   аварии остаётся консервативно блокирующей.
7. Cooldown истекает через один календарный месяц в Europe/Moscow, после чего
   запись удаляется. X-Forwarded-For игнорировать, кроме явного списка
   trusted reverse proxies.

### 5.6. Мобильный сервис и policy

1. Реализовать единый VpnSubscriptionService для verify/demo. Он формирует
   endpoint только из DRAGONET_PROXY_DOMAIN/PATH, добавляет request ID на
   каждый POST и валидирует ответ до использования.
2. Mpei-App-Req-Id строится как DragoNet-DD-MM-YYYY-DEVICE_STRING с московской
   датой. Неблокирующе получить разрешённый API serial, если он уже доступен;
   иначе штатно использовать название/версию ОС и модель. Не добавлять новые
   опасные runtime permissions ради serial.
3. Создать чистый extractVpnClientName(link): принимает только HTTPS и
   разрешённый origin/path prefix, берёт последний непустой segment, применяет
   decodeURIComponent ровно один раз, не меняет case/[]/@/_ и отклоняет
   чужой host, неверный path, пустое/слишком длинное имя и не-URL.
4. Результаты transport: ACTIVE, INACTIVE_CONFIRMED, TRANSIENT_FAILURE,
   OFFLINE_SKIPPED. reqStatus failed, timeout, socket close и malformed
   response — TRANSIENT_FAILURE, а не доказательство отсутствия подписки.
5. Persistent state:

   ~~~ts
   type VpnVerificationState = {
     clientName?: string
     lastVerifiedAt?: string
     technicalFailureStreak: number
     firstTechnicalFailureAt?: string
     inactiveStreak: number
     firstInactiveAt?: string
     lastEffectiveStatus: 'ACTIVE' | 'GRACE' | 'REVOKED' | 'NONE'
   }
   ~~~

6. Политика:

| Результат | Счётчики | Доступ |
| --- | --- | --- |
| ACTIVE | сбросить обе streak, обновить lastVerifiedAt | ACTIVE |
| INACTIVE_CONFIRMED | увеличить inactive, сбросить technical | grace до порога C |
| TRANSIENT_FAILURE | увеличить technical, сбросить inactive | grace до A/B |
| OFFLINE_SKIPPED | ничего не менять | прежний статус |

   Доступ отзывается только при A: technicalFailureStreak >= 10; B:
   technicalFailureStreak >= 3 и прошло не менее 7 суток с первого такого
   сбоя; C: inactiveStreak >= 3 и прошло не менее 3 суток с первого
   подтверждённого inactive.

7. Автопроверка запускается один раз после core gate успешной online-цепочки
   БАРС и выполняется в фоне. Ручная «Проверить снова» использует ту же policy.
   При отсутствии clientName status NONE; offline не меняет counters.
8. ACTIVE/GRACE публикует APP_EVENTS.VPN_ENTITLEMENT_CHANGED. Реклама и
   rewarded выключены; TokenBadge показывает ∞, реальные токены и покупки
   сохраняются. После REVOKED возвращаются только неприобретённые ограничения;
   купленное ad-free остаётся.

## Этап 6. Тесты и GitHub Actions

### Автоматические тесты

Не добавлять массовые snapshot-тесты. Новые тесты покрывают правила, в которых
регрессия меняет вход, данные, рекламу, деньги или доступ.

| Область | Обязательные сценарии |
| --- | --- |
| STUDENTS_NOT_FOUND | каждый допустимый месяц, любой другой месяц, post-2FA граница, неверный код, уже полученный student, credentials, logout/retry, маска пароля |
| Loading progress | success/fail переход, быстрая смена этапов, изоляция двух сессий, cleanup/unmount, fallback label |
| Core/background BARS | навигация после core, второстепенные задачи не блокируют, terminal FAILED, stale generation не dispatch-ит |
| Login Help | accordion, кнопка регистрации без видимого URL, обработка недоступного external URL |
| Ad placements | точное сопоставление ключ/ID, demo fallback, все inline/sticky props, скрытие при ad-free/VPN, padding и один sticky |
| Guest schedule | баннер только при пустом query; до submit нет fetch/Redux personal schedule |
| VPN URL parser | percent encoding, []/@, неверные host/path/protocol, пустой segment, не-URL |
| VPN policy | ACTIVE reset, transient, inactive 1–3/72 часа, transient 3/7 дней, transient 10, offline без изменения counters |
| Mobile transport | domain/path, московская дата, device fallback, mapping response, demoSubURL не попадает в storage |
| DragoNet result sheet | копирование по строке и иконке, iOS/Android тексты и кнопки, URL не отображается, закрытие удаляет demo URL |
| Proxy discovery | IP vote 3/3 и 2/3, нет кворума, приоритет LE, fallback только после него, DNS/IP и cert/key match |
| Proxy gate/verify | неверный header без HTTP-ответа, точные JSON поля, отсутствие Token/name/raw IP/device в response/log |
| Proxy demo/cooldown | payload, имя, отсутствие сохранения password/UUID, IP/device cooldown, календарный месяц, concurrency не более одного demo |
| Регрессии v2.4 | token economy, unlock/VPN override, Android icon confirmation и базовый App render с моками native SDK |

Добавить scripts typecheck: tsc --noEmit и test:ci: jest --ci --runInBand.
Добавить lint только после подтверждения стабильного non-watch запуска с
совместимой версией ESLint. Proxy имеет собственные install/typecheck/test
scripts и изолированную временную SQLite-базу.

Нативные flows (launcher aliases, реальные Yandex размеры/logcat, карта,
камера, App Store/APK handler) остаются ручной Android/iOS-приёмкой: Jest не
заменяет PackageManager и SDK.

### GitHub Actions

Создать .github/workflows/ci.yml:

~~~yaml
on:
  push:
    branches: [dev, v2]
  pull_request:
    branches: [dev, v2]
~~~

Jobs:

1. mobile-quality — checkout, Node 24, Yarn Classic cache,
   yarn install --frozen-lockfile, typecheck, test:ci и lint, когда готов.
2. metro-smoke — чистый Yarn install, background Metro с timeout/polling
   health endpoint, вывод логов при ошибке и гарантированная остановка.
3. android-debug-apk — Node 24, подтверждённый JDK (24 при возможности,
   fallback 17), debug assemble, опциональный artifact APK. Материализовать
   google-services.json из GitHub Secret только если debug build действительно
   этого требует.
4. vpn-proxy-quality — отдельная воспроизводимая установка в
   vpn-subscription-proxy, typecheck/test с mock panel, DNS/IP/TLS и temporary
   SQLite; без запросов к реальному VPS, IP-сервисам, сертификатам или панели.

В mobile CI не передавать VPN_PANEL_TOKEN, panel URL, proxy .env, release
keystore или production advertising IDs. Production proxy развёртывается
отдельным systemd workflow на VPS, а не из GitHub Actions мобильного проекта.

## Условия готовности

- Вход с отсутствующим Личным кабинетом не маскируется под неверный логин или
  пароль и не теряет credentials.
- Пользователь видит живой, понятный прогресс и получает навигацию после
  student/marks/debts/week/schedule, не после всех второстепенных разделов.
- Все inline/sticky места имеют отдельный конфигурационный ключ и не
  перекрывают контент.
- Demo DragoNet копируется одним нажатием, содержит корректную инструкцию
  именно для текущей платформы и не сохраняется после закрытия результата.
- DragoNet proxy fail-closed при невалидной identity/TLS-конфигурации и не
  раскрывает секреты.
- Unit/integration/component-тесты и CI покрывают критические правила,
  Android и iOS ручные gate пройдены.
- Версия v2.5.0 и WhatsNew отражают только реально завершённый объём.
