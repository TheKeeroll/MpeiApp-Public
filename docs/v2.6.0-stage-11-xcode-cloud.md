## CocoaPods: почему появился 1.15.2 и что обновить

В репозитории сейчас:

| Файл | Состояние |
| --- | --- |
| Gemfile | После реализации: CocoaPods = 1.17.0, xcodeproj = 1.28.1, Ruby >= 3.2 и < 3.5 |
| Gemfile.lock | CocoaPods 1.15.2, xcodeproj 1.25.1, Ruby 3.2.2, Bundler 2.4.10 |
| ios/Podfile.lock | COCOAPODS: 1.15.2; native SDK медиации уже обновлены 21.10 |

Прежнее ограничение `xcodeproj < 1.26.0` было несовместимо с CocoaPods 1.16.2:
тот требует xcodeproj >= 1.27.0. По этим ограничениям выбор более старого
CocoaPods при разрешении текущего Gemfile закономерен; точные команды
предыдущей macOS-сессии не устанавливались. Глобальная установка 1.16.2 не меняет
версию, которую запускает `bundle exec`. См. [зависимости 1.16.2](https://rubygems.org/gems/cocoapods/versions/1.16.2/dependencies).

На дату проверки свежий стабильный выпуск — **CocoaPods 1.17.0** от 06.07.2026,
а **xcodeproj — 1.28.1**. Опубликованный gem CocoaPods требует xcodeproj
>= 1.28.1 и < 2.0, а также ruby-macho ~> 4.1.0. Целевой набор подготовки —
**1.17.0 + 1.28.1**, с реальной проверкой проекта на Mac. Подтверждения:
[RubyGems CocoaPods](https://rubygems.org/gems/cocoapods),
[зависимости 1.17.0](https://rubygems.org/gems/cocoapods/versions/1.17.0/dependencies),
[RubyGems xcodeproj](https://rubygems.org/gems/xcodeproj).

Агент обновил ограничения Gemfile; пользователь на Mac выполнит resolver
и сохранит настоящий Gemfile.lock. Preflight останавливает Cloud до обновления
Gemfile.lock/Podfile.lock, вместо установки старого набора. Совместимость остальных Ruby gems и
Bundler проверяется на выбранном Ruby, без массового обновления pod SDK.
Cloud затем устанавливает этот же набор через Bundler. Встроенный в образ
глобальный CocoaPods не является источником версии проекта.

## iOS 15.6 и выбор Xcode

**Минимум приложения сохраняется 15.6.** В текущей таблице Apple deployment
targets Xcode 27/27.1 включают iOS 15. При этом device support и Simulator
у этих Xcode начинаются с iOS 17: это отдельные ограничения инструментов,
не требование повысить минимальную ОС собираемого приложения.
См. [таблицу совместимости Xcode](https://developer.apple.com/xcode/system-requirements).

Требование App Store с 28.04.2026 — сборка Xcode 26+ и SDK iOS 26+;
объявленный минимальный deployment target с 09.09.2026 — iOS 13.
Эти требования совместимы с 15.6. См. [требования Apple](https://developer.apple.com/news/upcoming-requirements/).
Локально React Native 0.87.1 также допускает 15.1
(`node_modules/react-native/scripts/cocoapods/helpers.rb`), а Podfile и app/test
targets уже используют 15.6. Виджет независимо требует **iOS 17.0** из-за
интерактивности AppIntent; это не повод повышать минимум всего приложения.

Выбрать стабильный образ Xcode 26+ из **реально доступных в Cloud** и проверить
его с обновлёнными Ruby gems/Pods; записать точные Xcode/macOS/Ruby/Bundler.
Xcode 27.1 опубликован 15.10.2026, но его наличие в Cloud нельзя выводить из
наличия локального релиза. Локальный Xcode выбирается также по доступной macOS
(для 27.1 требуется 26.6+). См. [релиз 27.1](https://developer.apple.com/news/releases/?id=10152026a)
и [выбор окружения Cloud](https://developer.apple.com/documentation/xcode/xcode-cloud-workflow-reference).

Проверить итоговый `MinimumOSVersion` в архиве; при наличии тестировщика с
iOS 15.6 — запуск приложения через TestFlight. Отсутствие старого Simulator
в новом Xcode не считать причиной прекращения поддержки iOS 15. Изменять
minimum только при установленной несовместимости зависимости и с отдельным
обоснованием. Публичного требования отказаться от 15.6 на дату проверки нет.

## Роли и подпись после переноса приложения

Пользователь — **Admin App Store Connect** текущего аккаунта, второй разработчик —
**Account Holder**. Apple допускает Admin к настройке workflow; роль владельца
не требуется для каждого действия с Cloud. Но если членство индивидуальное,
приглашённый пользователь ASC не становится членом команды Developer Program
и не получает её ресурсы подписи. Поэтому одноразовую настройку команды,
App Group и Cloud на MacBook планируем владельцу, если целевая Team недоступна
пользователю в Xcode. Для организации Admin с нужными ресурсами может сделать
это сам. Источники: [настройка Cloud и роли](https://developer.apple.com/xcode-cloud/get-started/),
[пользователи индивидуального аккаунта](https://developer.apple.com/help/app-store-connect/manage-your-team/add-and-edit-users/).

Владелец проверяет **нынешние**, уже использованные им для последних архивов
Team, app/extension identifiers и App Group. Существующий `DEVELOPMENT_TEAM`
в файле проекта не доказывает принадлежность правильному аккаунту. Сохраняются
bundle IDs `ru.NoobDragons.MpeiApp` и `ru.NoobDragons.MpeiApp.ScheduleWidget`;
App Group обеих целей сверяется с правами получателя приложения. Перенос уже
состоялся, повторять его не нужно. См. [App Groups после transfer](https://developer.apple.com/help/app-store-connect/transfer-an-app/overview-of-app-transfer/).

| Действие | Пользователь Admin | Владелец |
| --- | --- | --- |
| Локальная проверка зависимостей/Simulator | Да, без подписи целевой команды | Может повторить тот же проверенный набор |
| Первая настройка Cloud в Xcode | Если доступна нужная Team | Выполняет для индивидуального аккаунта/при отсутствии Team у Admin |
| Workflow, триггеры, логи, тестеры, Next Build Number в ASC | Выполняет после onboarding | Постоянное участие не требуется |
| Secret/shared variables Cloud | Выполняет, если не включён Only the Account Holder | Нужен при этом ограничении |
| Членство, обязательные соглашения, тариф часов | Не заменяет Account Holder | Проверяет/принимает при необходимости |

Флаг **Restrict Editing** workflow оставляет редактирование Admin/App Manager.
Он отличается от **Only the Account Holder** у shared variables. Для обычного
сопровождения Admin последний флаг не включать. Источники:
[управление workflow](https://developer.apple.com/documentation/xcode/developing-a-workflow-strategy-for-xcode-cloud),
[общие переменные Cloud](https://developer.apple.com/documentation/xcode/sharing-environment-variables-across-xcode-cloud-workflows).

## Конфигурация без GitHub repository secrets

Repository secrets GitHub не являются источником конфигурации Xcode Cloud.
Их создание/дублирование, API для выгрузки и private-репозиторий конфигурации
**не входят в этап 11**. Используется существующая передача файлов владельцу
для первоначальной настройки, затем **Cloud Secret/shared variables** и
генератор из части A. Обычные облачные сборки больше не требуют пересылки файлов.
Для отдельной локальной сборки по-прежнему нужна локальная конфигурация.

Значения вносит пользователь Admin или владелец при первом onboarding;
новые значения обновляются непосредственно в Cloud. Обязательные поля/имена
видны в публичной инструкции, значения и исходные файлы остаются закрытыми.
Серверные токены proxy и S-UI не относятся к конфигурации мобильного приложения.
Источники и ограничения GitHub сохранены в [исследовании](v2.6.0-xcode-cloud-research.md#repository-secrets-возможности-и-ограничения).
