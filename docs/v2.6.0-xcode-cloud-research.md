# Xcode Cloud для MpeiApp: сборки, TestFlight и секреты

Дата исследования: **18.10.2026**, уточнено **22.10.2026**. Изучены [исходная документация Xcode Cloud](https://developer.apple.com/documentation/xcode/xcode-cloud)
и связанные материалы Apple о настройке проекта, GitHub, условиях запуска,
зависимостях, скриптах, переменных, распространении и диагностике. Также
проверены документация GitHub и текущее устройство репозитория.

## Вывод

**Xcode Cloud применим к MpeiApp.** Можно настроить автоматические iOS Archive
и загрузку в существующую карточку MpeiApp в App Store Connect/TestFlight.
Постоянно работающий собственный Mac и отдельный платный сервис CI не нужны.
Первоначальное подключение выполняется в Xcode на Mac; затем управлять
workflow и читать результаты можно через браузер, в том числе из Windows.
Это подтверждают [требования Apple](https://developer.apple.com/documentation/xcode/setting-up-your-project-to-use-xcode-cloud)
и [настройка первого workflow](https://developer.apple.com/documentation/xcode/configuring-your-first-xcode-cloud-workflow).

Дополнительная подписка на Xcode Cloud **не обязательна**: Apple Developer
Program включает 25 вычислительных часов в месяц. Это ограниченный бюджет,
поэтому бесплатность нельзя обещать для неограниченного количества push.
Исследование подтверждает применимость подхода; фактическая облачная сборка
MpeiApp ещё не запускалась.

По решению 22.10 конфигурация хранится только в **Xcode Cloud Secret variables**;
GitHub repository secrets для этой задачи не создаются. Существующая передача
файлов владельцу Apple-аккаунта сохраняется для первого подключения. Затем
Cloud восстанавливает их сам. Ограничения GitHub Secrets описаны ниже для справки.
Совместимость CocoaPods/iOS и разделение действий Admin/Account Holder — в
[актуализации этапа 11](v2.6.0-stage-11-xcode-cloud.md).

## Подписка, стоимость и права

Достаточно обычного **индивидуального Apple Developer Program**. Организация,
Enterprise Program и платный GitHub Team для этого сценария не требуются.
Стандартная цена Developer Program — 99 USD в год; региональные цены могут
отличаться. Для индивидуальной регистрации требуется Apple Account с 2FA.
См. [условия регистрации Apple](https://developer.apple.com/programs/enroll/).

Тарифы Xcode Cloud на дату проверки:

| Вычислительные часы в месяц | Цена сверх обычного членства Developer Program |
| --- | --- |
| 25 | Включены в членство |
| 100 | 49.99 USD/месяц |
| 250 | 99.99 USD/месяц |
| 1 000 | 399.99 USD/месяц |
| 10 000 | 3 999.99 USD/месяц |

Покупку дополнительных часов оформляет Account Holder. Неиспользованные
часы не переносятся. Compute time учитывает выполняемые задачи, поэтому
параллельные действия могут расходовать больше времени, чем длительность
сборки по часам. Источник: [Apple — подписки и compute hours](https://developer.apple.com/xcode-cloud/get-started/).

Для MpeiApp предлагается сохранить включённый тариф и выполнять в Cloud
один iOS Archive на событие. Проверки JS/TypeScript и proxy уже есть в GitHub
Actions. После первых запусков нужно оценить расход в
[App Store Connect → Users and Access → Xcode Cloud](https://developer.apple.com/documentation/xcode/reviewing-xcode-cloud-usage-data).
Например, при расходе 30 compute minutes на запуск 25 часов дают около
50 запусков, при 60 минутах — 25. Это расчёт бюджета, а не измеренная скорость
MpeiApp. При приближении к лимиту — приостанавливать запуски до следующего
периода, если владелец не выбирает платный тариф.

Для подключения GitHub нужен владелец организации либо admin личного
репозитория. Apple предлагает установить свой GitHub App только для нужного
репозитория. Публичность исходников не отменяет это подключение.
См. [Connecting Xcode Cloud to GitHub](https://developer.apple.com/documentation/xcode/connecting-xcode-cloud-to-github).

В App Store Connect нужны права на MpeiApp; первоначальную настройку Apple
разрешает Account Holder, Admin и App Manager. Но приглашённые пользователи
индивидуального аккаунта не становятся участниками Developer Program team
и не получают её ресурсы подписи. Для MpeiApp разовое подключение на Mac
планируется владельцу, если Team недоступна Admin; в организации с нужными
ресурсами Admin может выполнить его сам. После onboarding Admin сопровождает
workflow, конфигурацию и TestFlight в браузере; владельцу остаются особые
вопросы членства/соглашений/подписи и ограниченных переменных.
См. [права настройки Cloud](https://developer.apple.com/xcode-cloud/get-started/)
и [пользователи индивидуального аккаунта](https://developer.apple.com/help/app-store-connect/manage-your-team/add-and-edit-users/).

## Триггеры: dev с тегом и любой push в v2

Apple поддерживает Branch Changes и Tag Changes, в том числе фильтры
конкретных веток и префиксов тегов. Несколько start conditions работают
как альтернативы: добавление двух условий не создаёт логическое AND.
См. [Configuring start conditions](https://developer.apple.com/documentation/xcode/configuring-start-conditions).

Предлагаются два workflow с общей подготовкой зависимостей:

| Workflow | Условие запуска | Архив и результат |
| --- | --- | --- |
| MpeiApp dev TestFlight | Tag Changes: теги с префиксом `ios-dev-`, например `ios-dev-2.6.0-beta.1`; дополнительная проверка коммита в `dev` | Release Archive, TestFlight and App Store, Restrict Editing, группа тестеров; пригодна для App Review |
| MpeiApp v2 TestFlight | Branch Changes: ровно `v2`, без фильтров файлов/папок | Release Archive, TestFlight and App Store, внутренняя группа; возможность позднее отправить эту сборку на App Review |

Git-тег указывает на объект/коммит и не хранит единственную «свою ветку».
Поэтому «тег в dev» необходимо определить как соглашение: сначала коммит
попадает в remote `dev`, затем на него публикуется тег нужного префикса.
См. [модель git tag](https://git-scm.com/docs/git-tag).

Для проверки в подготовительном скрипте нужно получить `origin/dev` и
достаточную историю, затем проверить
`git merge-base --is-ancestor "$CI_COMMIT" origin/dev`. Это допускает
помеченный коммит из истории `dev`, даже если ветка уже продвинулась дальше.
Равенство текущему HEAD ветки было бы более узким и подверженным гонкам условием.
Основание: [git merge-base](https://git-scm.com/docs/git-merge-base).

Для tag-trigger Apple предоставляет `CI_TAG` и `CI_COMMIT`; наличие
`CI_BRANCH=dev` для него предполагать нельзя. Нативный Tag Changes фильтрует
имя тега, а не принадлежность коммита ветке. Проверка неподходящего коммита
должна завершать подготовку с понятной ошибкой до установки зависимостей.
См. [переменные Xcode Cloud](https://developer.apple.com/documentation/xcode/environment-variable-reference)
и [Tag Start Condition API](https://developer.apple.com/documentation/appstoreconnectapi/citagstartcondition).

Если требуется вообще не создавать Cloud build для тега вне `dev`,
можно вместо нативного tag-trigger использовать небольшой GitHub Actions
workflow: событие тега → проверка истории `dev` → запуск Cloud через
[App Store Connect API](https://developer.apple.com/documentation/appstoreconnectapi/xcode-cloud-workflows-and-builds).
Это требует отдельного API credential. Для основного предложенного варианта
с нативными триггерами такой ключ не нужен.

Тег должен быть отправлен на GitHub: локального `git tag` недостаточно.
Обычный push в `dev` без нового подходящего тега не запускает этот Cloud
workflow. GitHub Actions при этом продолжает выполнять свой существующий CI.

По умолчанию Cloud включает Auto-cancel Builds: следующий push может
отменить предыдущую сборку того же workflow. Если требуется TestFlight-сборка
для **каждого** push в `v2`, Auto-cancel нужно выключить. При включённом
режиме часть промежуточных коммитов может не дать сборку TestFlight.
Источник: [workflow reference — Auto-cancel Builds](https://developer.apple.com/documentation/xcode/xcode-cloud-workflow-reference).
Также не следует добавлять `[ci skip]` в такие коммиты. Лимит часов,
ошибки сборки и обработки Apple остаются возможными причинами отсутствия
готовой сборки в TestFlight.

Подготовку Node, Yarn, Ruby/Bundler, patches и Pods нужно выполнять в
`ios/ci_scripts/ci_post_clone.sh`, расположенном рядом с workspace. Переходить
в корень следует через `CI_PRIMARY_REPOSITORY_PATH`, а не предполагать текущий
каталог. Для скриптов нужны shebang, LF и корректные права исполнения в Git.
Экспорт PATH из одного скрипта нельзя считать настройкой всех следующих
процессов: отдельно проверить Node в RN bundle phase. Apple описывает эти
точки расширения в [Writing custom build scripts](https://developer.apple.com/documentation/xcode/writing-custom-build-scripts).

После разового обновления lockfile на Mac в CI устанавливается именно
проверенный набор: `yarn install --frozen-lockfile`, `bundle install`,
затем `bundle exec pod install --deployment` из `ios`. Установка Pods
поддерживается Cloud; переносить весь проект на Swift Package Manager не
требуется. См. [зависимости и CocoaPods](https://developer.apple.com/documentation/xcode/making-dependencies-available-to-xcode-cloud).
Устаревший bitcode stripping отсутствующих LogRocket/старых путей Hermes удалён;
сохранён React Native post_install. Несовместимое `< 1.26.0` заменено явным
xcodeproj 1.28.1. Resolver 1.17.0/1.28.1 и native-проверка остаются на Mac.
Источники и порядок resolver — в [проверке инструментов](v2.6.0-stage-11-xcode-cloud.md#cocoapods-почему-появился-1152-и-что-обновить).

Для первой приёмки выбрать доступный стабильный Xcode 26+ с учётом
требований App Store к SDK и выбранного Chartboost SDK; обоснование приведено в
[инструкции медиации](v2.6.0-ios-mediation.md). Конкретный доступный образ
проверяется в настройках Cloud. Вместо `yarn ios`, запускающего локальную
сборку/симулятор, сам Cloud выполняет настроенное действие Archive.

App Store Connect запись MpeiApp уже существует. Нужно выбрать её,
подтвердить signing обоих targets и сохранить bundle IDs. Apple требует
[automatic signing и общую схему](https://developer.apple.com/documentation/xcode/setting-up-your-project-to-use-xcode-cloud);
экспортировать личный `.p12` в публичный репозиторий для этого не требуется.

Cloud автоматически увеличивает build number. Для уже использованной версии
нужно исключить совпадения с ранее загруженными сборками; при необходимости
задать Next Build Number в App Store Connect. Новая версия iOS может начинаться
с меньшего номера, чем предыдущая версия: уникальна комбинация версии и build.
Git-тег не меняет MARKETING_VERSION автоматически. Оба workflow должны быть
в одном продукте MpeiApp: общий CI_BUILD_NUMBER применяется ко всем целям
скриптом перед xcodebuild, не сбрасываясь по ветке. Версия может оставаться
2.6.0 при росте build numbers. Опубликованный проверенный dev-бинарный файл
выбирается для App Review по его номеру без запуска нового Archive.
См. [правила build numbers](https://developer.apple.com/documentation/xcode/setting-the-next-build-number-for-xcode-cloud-builds).

## TestFlight и диагностика

В workflow необходимы Archive и подходящий post-action TestFlight.
`TestFlight Internal Testing Only` не подходит для последующей отправки этого
же бинарного файла на App Review или внешним тестерам. По уточнению 22.10
**оба** workflow используют `TestFlight and App Store`, Restrict Editing и выбранную
группа тестеров. В настройках workflow для распространения Apple рекомендует
Clean; для внешнего TestFlight чистая сборка обязательна и увеличивает расход
времени. Это нужно учесть при замере бюджета. Для внешнего TestFlight требуется beta app review;
выпуск в App Store всё равно оформляется отдельно.
См. [workflow для распространения](https://developer.apple.com/documentation/xcode/creating-a-workflow-that-builds-your-app-for-distribution).
Условия кэширования описаны в [workflow reference](https://developer.apple.com/documentation/xcode/xcode-cloud-workflow-reference#Perform-a-clean-build).

После успешного архива Cloud сам загружает сборку в App Store Connect.
Появление готовой сборки у тестеров зависит также от processing Apple,
экспортных деклараций и настроек группы.
См. [TestFlight distribution](https://developer.apple.com/documentation/xcode/distributing-your-xcode-cloud-builds-through-testflight).

Ошибка сборки сохраняется в истории Cloud, даже если в TestFlight ничего
не появилось. Путь из браузера: **App Store Connect → My Apps → MpeiApp →
Xcode Cloud → Builds → нужный запуск → неудачное действие → Logs**.
Там же доступны статус, commit, этапы и артефакты; в Xcode это Report navigator
→ Cloud. Можно настроить уведомления об ошибках. Артефакты Cloud хранятся
до 30 дней, поэтому release-архивы и dSYM следует сохранять отдельно.
Источник: [первый workflow, журналы и артефакты](https://developer.apple.com/documentation/xcode/configuring-your-first-xcode-cloud-workflow).

## Repository secrets: возможности и ограничения

Публичный репозиторий может использовать GitHub Actions repository secrets.
Их значения не становятся частью исходников или доступного всем списка
переменных. Но после сохранения GitHub не предоставляет чтение значения
через UI/API: REST возвращает сведения о секрете, например имя и даты.
`gh secret list` также не возвращает значения.
См. [использование secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)
и [Get a repository secret](https://docs.github.com/en/rest/actions/secrets#get-a-repository-secret).

Под «contributors» здесь следует понимать явно приглашённых доверенных
collaborators, а не любого автора принятого PR. Само присутствие в списке
Contributors не даёт прав на секреты. При этом автор workflow с write-доступом
практически может получить переданные сборке значения через исполняемый код.
GitHub прямо относит пользователей с write к имеющим доступ к repository secrets.
См. [доступ и безопасное использование](https://docs.github.com/en/actions/reference/security/secure-use).

| Сценарий | Доступ к значениям |
| --- | --- |
| Читатель публичного репозитория | Не получает plaintext secrets через GitHub UI/API |
| Внешний PR из fork | GitHub Actions не передаёт repository secrets по умолчанию, кроме специального `GITHUB_TOKEN` |
| Доверенный collaborator и разрешённый workflow | Workflow получает указанные секреты во время выполнения; прочитать старое значение кнопкой в настройках нельзя |
| Xcode Cloud | Получает собственные Secret environment variables, а не `${{ secrets.* }}` GitHub Actions |
| Разработчик собирает локально | Нужна отдельно выданная конфигурация или доступ к закрытому хранилищу |

Для автоматизации сохраняются `.gitignore` и публичный `Secrets.example.ts`.
**В этапе 11 настраиваются только Secret environment variables Xcode Cloud**;
создание repository secrets для GitHub Actions исключено по уточнению 22.10.
При нескольких workflow Apple позволяет использовать
[shared environment variables](https://developer.apple.com/documentation/xcode/sharing-environment-variables-across-xcode-cloud-workflows).
Значения вводятся в Cloud Admin либо владельцем при первом подключении и
применяются к обоим workflow; дальнейшие обновления выполняются там же.
Флаг Only the Account Holder ограничивает редактирование общих переменных:
для сопровождения Admin его оставляют выключенным. Restrict Editing самого
workflow — другое ограничение, оно сохраняет возможность редактирования Admin.

Публичный генератор должен восстанавливать `Secrets.ts` и Swift initializer
из входных переменных, проверять обязательные поля для production и не
выводить значения. Примеры имён: `MPEIAPP_YANDEX_MAPS_API_KEY`,
`MPEIAPP_DRAGONET_PROXY_DOMAIN`, `MPEIAPP_DRAGONET_PROXY_PATH` и отдельные
`MPEIAPP_YANDEX_AD_IOS_*` / `MPEIAPP_YANDEX_AD_ANDROID_*` для placement IDs.
Один maps key должен согласованно попадать в JS и Swift.

Отдельные секреты предпочтительнее большого JSON/base64 со всем файлом:
маскирование может не распознать распакованные или преобразованные значения.
Base64 также не является шифрованием. Не выводить `env`, содержимое
сгенерированных файлов или их значения в ошибки.
Основание: [рекомендации GitHub по маскированию](https://docs.github.com/en/actions/reference/security/secure-use)
и [Base64 secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets#storing-base64-binary-blobs-as-secrets).

Существующие четыре GitHub jobs могут продолжать использовать публичную
заглушку, как сейчас. Production-конфигурация нужна доверенной сборке;
её не следует передавать коду внешних PR через обходные privileged workflows.
В предложенных Cloud workflow PR-trigger вообще не включается.
Правила fork/Dependabot описаны в [GitHub Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets#using-secrets-in-a-workflow).

### Существующий закрытый канал и дальнейшие сборки

Передача клиентских файлов владельцу Apple-аккаунта уже организована.
Она используется при первоначальной локальной подготовке; отдельный private
репозиторий для Cloud не создаётся. После настройки Secret variables и
генератора обычные облачные сборки не требуют пересылки файлов. Для локальной
сборки участнику по-прежнему нужна локальная конфигурация: GitHub/Cloud Secrets
не становятся хранилищем для чтения сохранённых значений через интерфейс.

### Граница конфиденциальности клиентских значений

GitHub/Cloud secrets скрывают значения от читателей репозитория, но значения,
которые попали в готовое мобильное приложение, можно извлечь из его bundle.
Это относится к maps key, рекламным placement IDs и настройкам endpoint,
даже если исходный `Secrets.ts` никогда не публиковался.
См. [React Native — Storing Sensitive Info](https://reactnative.dev/docs/security#storing-sensitive-info).

Поэтому в сборку передаётся только клиентская конфигурация из публичного
шаблона. Данные доступа к S-UI, серверные токены, HMAC-ключи и содержимое
`vpn-subscription-proxy/.env` остаются на сервере и не переносятся в эту схему.
